# M5b · Check-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A PT shows a rotating, offline-capable QR code (with a 6-digit fallback) for a booking; the client scans or types it and is checked in; a second scan, the PT, or completing the logged session checks them out; the client rates the session and opens a receipt with the PT's recorded amount; the PT saves reminder preferences that are not sent yet.

**Architecture:** Migration `0021` adds a server-only per-booking secret table, reminder settings, amount/receipt/rating columns on `bookings`, a default price on `booking_rules`, two triggers, and RPCs (`checkin_keys`, `check_in`, `check_out`, `rate_booking`, `set_booking_amount`, `save_reminder_settings`), and re-creates `rules_for`, `save_availability`, `start_workout_session` and `complete_workout_session` with the minimum change. `packages/shared/src/checkin/` holds the HMAC code, the QR payload format, receipt formatting, the error map and `PendingQueue` under vitest. Mobile gets a QR renderer, five screens and edits to four existing ones; the web admin's bookings table gains three columns.

**Tech Stack:** Supabase Postgres (plpgsql, pgcrypto `hmac`), `@noble/hashes` (HMAC-SHA256 in Hermes and the browser), `qrcode-generator` (QR matrix, rendered with `react-native-svg`), `expo-camera` barcode scanning, zod 4, vitest 2, Expo SDK 57, Next.js 16.

**Spec:** `docs/superpowers/specs/2026-10-11-m5b-check-in-design.md` (D1–D15). Design: `docs/Forge M5 Scheduling.html` screens 05, 07, 11, 12, 13. Tracker: `docs/M5_Scheduling.md`. The user waived review of spec and plan; record deviations in **As built**.

## Global Constraints

- Every write to `check_ins`, `bookings`, `booking_checkin_keys`, `reminder_settings` is an RPC. `anon`/`authenticated` hold no INSERT/UPDATE/DELETE on them, and no privilege at all on `booking_checkin_keys`.
- Code: window `w = floor(epoch_seconds / 60)`; message `"<booking uuid lowercase>:<w>"` UTF-8; HMAC-SHA256 with the 32-byte secret; offset = `mac[31] & 0x0f`; `bin = (mac[o] & 0x7f) << 24 | mac[o+1] << 16 | mac[o+2] << 8 | mac[o+3]`; code = `bin mod 1 000 000`, zero-padded to 6.
- Shared vector: secret `000102…1f` (hex of bytes 0..31), booking `5b000000-0000-4000-8000-0000000000c1`, windows 29000000/29000001/29000002 → `104142`/`861886`/`701179`. Both vitest and the SQL harness assert it.
- QR payload: `forge-checkin:1:<booking_id>:<window>:<code>`.
- Check-in window: `starts_at − 30 min ≤ at ≤ ends_at`. QR window tolerance ±1; typed tolerance current and 3 previous. Re-scan checks out only at `checked_in_at + 10 min` or later. `p_at` clamped to `[now − 24 h, now]`.
- Amounts are integer cents, USD, ≥ 0, ≤ 100 000 00 (100 000 USD).
- Receipt label: `FRG-<YYYY of starts_at in device time>-<receipt_no padded to 5>`.
- Rating 1–5 integer; comment ≤ 500 chars, trimmed, empty → null.
- Errors are raised as bare tokens; `not authorized` keeps ERRCODE `42501`.
- Screens: own `NavHeader` + `router.dismissTo` back (N1/N15); refetch on focus (N12); newest load wins (O1); `replace` after a state-changing submit (N3); every `{{name}}` has a no-name variant (I3); en/ar key parity.

## Review Focus

1. **A code replayed after it rotated** (photo of the screen shown later) — refused `code_expired`. Test: Task 1 (window − 2).
2. **A double scan at the door** — must not check the client straight out. Test: Task 1 (second scan at +1 min is `already`; at +11 min is `checked_out`).
3. **An offline scan replayed hours later** — still verifies against its own scan time, and replaying it twice is one check-in. Tests: Task 1 (`p_at` = 2 h ago inside the window) and Task 2 (`PendingQueue` dedupes by booking).
4. **Another client's code** — refused without naming anyone. Test: Task 1 (`wrong_booking`); the copy names only the scanner's own booking time.
5. **A session completed without any scan** — still completes the booking, gets a receipt number, and is ratable. Test: Task 1.

export function windowOf(ms: number): number;                 // floor(ms/1000/60)

## As built — deviations from this plan

- RPC result columns are prefixed `out_` (`out_booking_id`, `out_outcome`, …), as 0020's `save_availability` does, so they can't collide with plpgsql variables.
- `check_in`'s typed path checks `no_booking_now` before trying codes, so "nothing open" and "wrong digits" read differently. Junk input (not six digits) is `bad_code` without a lookup.
- `rate_booking` raises `bad_rating` for anything outside 1–5, and a later call without a comment keeps the one already left.
- `set_booking_amount` raises `bad_amount` outside 0…100 000 USD.
- `check_out` returns the booking, not a table; the PT path in `check_in` never checks anyone out.
- Reminders open from Settings and from Availability › Rules.
- The client's "Scan to check in" stays visible while checked in, because the second scan is the check-out.
- `useMyBookings` treats a `checked_in` booking as upcoming until it ends.
- The walk (`.claude/skills/forge-screen-walk/m5b/a.mjs`, gitignored) feeds Chrome a generated y4m of the live code (`--use-file-for-fake-video-capture`), so the web target exercises the real QR decode path. The camera re-reads the file each time it opens, so the script blanks it at the start.
- Two walk-found fixes: the scanner frame now follows the result's tone, and the QR's accessibility label moved from the SVG to a wrapping View (react-native-svg on web forwarded `accessible` to the DOM).
